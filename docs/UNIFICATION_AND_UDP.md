# Унификация прошивки PS-части модема ПКРВ + протокол управления (UDP)

Документ описывает:
1. **Унификацию** — единую прошивку с выбором роли/сети по сети, без перепрошивки.
2. **Полный протокол управления по UDP** — все команды (0x90, 0xA0, legacy).
3. Кратко — **watchdog**.

По умолчанию выбранные роль/IP/MAC действуют **в RAM** — до перезагрузки. Чтобы
они пережили ребут, конфиг можно сохранить во флэш QSPI командой `0x20` (см. §4.4).

---

## 1. Унификация — суть

Раньше под каждый режим (**master** / **slave**) собиралась отдельная прошивка, смена
режима = перепрошивка. Теперь — **одна прошивка**, режим и сетевые параметры
задаются командой по UDP на лету.

Что сделано:

- **Единый рантайм-конфиг** (`struct device_config current_config`): роль, IP/маска/шлюз,
  адрес соседа (peer), три MAC (GEM/radio/bridge), `device_id`. При старте сидируется
  из компайл-тайм `IS_MASTER`/`IS_SLAVE`, дальше меняется командами.
- **Смена роли на лету** (`device_reinit`, «мягкий»): без перезагрузки и без
  реинициализации GEM. Меняются IP (`netif_set_addr`), MAC (`hwaddr`), пересоздаются
  UDP-листенеры; в конце — gratuitous ARP, чтобы соседи сразу обновили MAC.
- **Смена MAC на лету:** MAC = запись в `netif->hwaddr` (GEM в promiscuous, исходящий
  src-MAC берётся из hwaddr). Меняются все три MAC.
- **Поиск модемов (broadcast discovery):** ПК шлёт широковещательный `get config`,
  каждый модем отвечает своими параметрами. Работает и когда IP модема неизвестен.
- **Уникальный `device_id`** (2 байта, временно master=1/slave=2): для **адресных**
  broadcast-команд — команда применяется только совпавшим модемом, остальные игнорируют.
- **`device_id` в каждом 188-байтном радио-сегменте** — задел под точка-многоточка
  (приёмник различает источник сегмента).

### 1.1. Сетевая архитектура

Модем — это мост (bridge) на три порта:

```
   GEM (Ethernet, port1) ─┐
                          ├─ bridge_netif (IP-стек модема)
   radio (vport3, port3) ─┘
```

- `bridge_netif` держит IP модема; GEM в **promiscuous**-режиме.
- MAC'и по умолчанию (различают роли):

| Параметр   | MASTER              | SLAVE               |
|------------|---------------------|---------------------|
| IP         | 192.168.250.11      | 192.168.250.21      |
| peer       | 192.168.250.22      | 192.168.250.10      |
| MAC GEM    | 00:1A:35:AA:BB:CC   | 00:0A:35:AA:BB:CC   |
| MAC radio  | 00:1A:35:DD:EE:03   | 00:0A:35:DD:EE:03   |
| MAC bridge | 00:1A:35:AA:BB:CE   | 00:0A:35:AA:BB:CE   |
| device_id  | 1                   | 2                   |

### 1.2. UDP-порты

| Порт        | Назначение                                            |
|-------------|-------------------------------------------------------|
| **60012**   | приём команд управления (0x90 / 0xA0 / legacy)        |
| 5007 / 5009 | статус-пакеты `stat_modem` (master → 5007, slave → 5009) |
| 5078        | IQ-стрим для созвездия (по запросу)                   |
| 5008        | видео/данные (RTP-приём)                              |

## 2. Диспетчеризация протоколов (порт 60012)

Первый байт пакета определяет протокол (`cmd_udp_callback`):

| Условие                        | Протокол                          |
|--------------------------------|-----------------------------------|
| `len ≥ 4` и `data[0] == 0xA0`  | **0xA0** — cregs / device config  |
| `len ≥ 2` и `data[0] == 0x90`  | **0x90** — основное управление    |
| `len ≥ 3` (иначе)              | **legacy ucnt** — firewall / IP   |

> Замечание: legacy-пакет отличается только «не 0xA0/0x90», а его `data[0..1]` — это
> счётчик `ucnt`. Теоретически возможна коллизия, если старший байт ucnt станет
> 0xA0/0x90 (на практике не встречается).

## 3. Протокол 0x90 — основное управление

Формат запроса: `90 <sub> [payload…]`. Ответы (где есть) начинаются с `90 <sub>`.

### 3.1. Запись (конфигурация радиотракта)

| Sub  | Назначение              | Payload (после `90 sub`)             | Ответ |
|------|-------------------------|--------------------------------------|-------|
| 0x02 | Установить TX-частоту    | freq `u64` LE, Гц (10 байт всего)     | —     |
| 0x03 | Установить RX-частоту    | freq `u64` LE, Гц                     | —     |
| 0x04 | TX-аттенюация            | `u32` LE, ×0.1 дБ (0..890)            | —     |
| 0x05 | Тест-генератор           | fcode `u32` LE + mask `u8` (7 байт)   | —     |
| 0x06 | RX-модуляция (par[23])   | `u8` (3 байта)                        | —     |
| 0x07 | TX-модуляция (par[22])   | `u8` (3 байта)                        | —     |
| 0x08 | GPIO/УФ управление       | qt_mask `u8` (биты: pit/tangenta/sel) | —     |
| 0x14 | AD9361 fastlock store    | `u8`: биты0-2 профиль, бит6 TX/RX     | —     |
| 0x15 | FHSS вкл/выкл             | `u8` (1=ON)                           | —     |
| 0x16 | NPU: панель вкл/выкл      | idx `u8` + enable `u8` (4 байта)      | —     |
| 0x17 | NPU: преселектор          | idx `u8` (3 байта)                    | —     |

### 3.2. Чтение

| Sub  | Назначение            | Ответ (после `90 sub`)                    |
|------|-----------------------|-------------------------------------------|
| 0x10 | TX-частота            | freq `u64` LE                             |
| 0x11 | RX-частота            | freq `u64` LE                             |
| 0x12 | TX-аттенюация         | `u32` LE, дБ                              |
| 0x13 | FPGA-регистр par[N]   | запрос `+ u8 N` (0..41); ответ: N + значение |

### 3.3. Диагностика

| Sub  | Назначение             | Детали                                                        |
|------|------------------------|--------------------------------------------------------------|
| 0x20 | Статистика             | ответ 78 байт: radio (9×`u32`) + lwIP (10×`u32`)              |
| 0x21 | Loopback get/set       | `len=3` → set `u8`; ответ `[2]`=состояние                     |
| 0x22 | Тест сегментации       | `[2]`=N кадров (1..16); ответ 82 байта (sent_ok + статистика) |
| 0x30 | FIFO: тест-запись блока | ответ: ok + счётчик + vacancy                                |
| 0x31 | FIFO: статус           | ответ: vacancy + occupancy + ISR                             |
| 0x32 | FIFO: сброс            | ответ `[2]`=ok                                               |
| 0x40 | Watchdog: статистика   | ответ 28 байт (reboot_status, kick/starve, uptime, crash-инфо) |
| 0x48 | Инфо о прошивке        | ответ: `[2]`=role_id (1=MASTER,2=SLAVE,0=мисконфиг), `[4..]`=ASCII версия |
| 0x4C | Watchdog: вкл/выкл      | `len=2` GET / `len=3` SET (`[2]`:0=выкл); ответ `[2]`=состояние |

## 4. Протокол 0xA0 — cregs и конфиг устройства

Формат: `A0 <group> <…>`. Группы **0..4** — прямая запись AXI-регистров
(cregs и пеленг), фиксированные 8 байт. Группа **5** — конфиг устройства
(унификация), переменная длина.

### 4.1. Группы 0..4 — запись cregs (по 8 байт)

Формат: `A0 <group> <creg> 00 <word[4] big-endian>` (`word` в `data[4..7]`, MSB первый).

| Group | Что                | creg (data[2])                                   |
|-------|--------------------|--------------------------------------------------|
| 0     | ppos (общие)       | 2 = creg2, 3 = creg3, 5 = creg5                  |
| 1     | tx_chan0           | 0 = creg0, 1 = creg1, 2 = creg2 (LO), 3 = creg3 (atten) |
| 2     | rx_chan0           | 0 = creg0, 1 = creg1 (LO)                        |
| 3     | статус-репортинг   | 0 = status_ip, 1 = `(status_on<<16) \| status_port` |
| 4     | пеленг (см. 4.2)   | 0..2 = creg0..creg2                              |

> Пример «включить статус на host:5007»: `A0 03 00 00 <hostIP BE>`, затем
> `A0 03 01 00 00 01 13 8F` (on=1, port=0x138F=5007).

### 4.2. Группа 4 — пеленг (импульсный сигнал)

Формат как у cregs: `A0 04 <creg> 00 <word[4] BE>`; пишется в
`AXI_CNTRL_REG1_BASEADDR + PELENG_PAR_OFFSET`.

| creg | Поля (`struct peleng`) |
|------|------------------------|
| 0    | `dut_imp:12`, `per_imp:16`, `run:1`, `barker:3` |
| 1    | `num_imp:10`, `num_group:10`, `per_group:12` (мс) |
| 2    | `freq_shift:32` |

### 4.3. Группа 5 — конфиг устройства (унификация)

Формат: `A0 05 <subcmd> <tidHi> <tidLo> <payload…>`
где **`tid`** (target device_id): `0` = всем, иначе применяет только модем с
совпавшим `device_id`. Команда изменения шлёт **ACK** до применения.

| Subcmd | Назначение   | Payload (после tid)                     | Длина | Ответ / ACK |
|--------|--------------|-----------------------------------------|-------|-------------|
| 0x00   | set role     | `role` (0=master, 1=slave)              | 6     | `A0 05 00 tid[2] 01` |
| 0x01   | set network  | `ip[4] mask[4] gw[4]`                    | 17    | `A0 05 01 tid[2] 01` |
| 0x02   | set MAC (все 3) | `mac_gem[6] mac_radio[6] mac_bridge[6]` | 23   | `A0 05 02 tid[2] 01` |
| 0x10   | get config   | — (target не нужен)                     | 4     | см. ниже    |
| 0x20   | save config (QSPI) | — (сохранить текущий конфиг во флэш) | 5     | `A0 05 20 tid[2] 01` |
| 0x21   | factory reset | — (стереть флэш-конфиг)                 | 5     | `A0 05 21 tid[2] 01` |

**Ответ на get config (0x10):**
```
A0 05 10 | device_id[2] | role[1] | ip[4] | peer[4] | mac_gem[6] | mac_radio[6] | mac_bridge[6]
```
Итого 32 байта.

> `set role` применяет **дефолты роли целиком** (IP, MAC, peer, device_id).
> `set network` / `set MAC` меняют только соответствующие поля, остальное сохраняется.

### 4.4. Персистентность конфига (QSPI)

`set role/network/MAC` меняют только **рантайм**-конфиг (в RAM) — после жёсткой
перезагрузки/пропадания питания вернутся дефолты прошивки. Чтобы настройки
пережили ребут, их надо **явно** сохранить командой `0x20`.

- **`0x20` save** — пишет текущий `current_config` во флэш QSPI. ACK — сразу,
  реальная запись отложена в main loop (стирание сектора блокирует ~1 с).
- **`0x21` factory reset** — стирает флэш-конфиг; при следующем старте модем не
  найдёт валидной копии и поднимется с дефолтами прошивки.

Реализация (`cfg_flash.c`): область `0x00F00000` (выше BOOT.BIN, в пределах
первого 16-МБ банка), **две копии A/B** с magic+version+seq+**CRC32**. Загрузка
берёт валидную копию с бо́льшим `seq`; сохранение пишет в НЕ-последний слот —
обрыв питания во время записи не портит вторую копию. Загрузка выполняется при
старте (`cfg_flash_load` в `main.c`) до применения роли/IP/MAC.

## 5. Legacy-протокол (ucnt) — firewall и set-IP

Формат: `<ucnt[2]> <cmd> [payload…]`. `ucnt` — эхо-счётчик (возвращается в ответе).

| Cmd  | Назначение            | Payload / ответ                                   |
|------|-----------------------|---------------------------------------------------|
| 0x05 | Firewall: установить  | `mask[4] arp icmp tcp udp` (11 байт)              |
| 0x06 | Firewall: запросить   | ответ 11 байт: mask + флаги                        |
| 0x07 | **Set IP (DEPRECATED)** | `ip[4] mask[4] gw[4]` (15 байт); ACK 8 байт      |

> **`0x07` устарел:** не имеет target — широковещательный `0x07` сменит IP **всем**
> модемам сразу. Для адресной смены использовать `0xA0 group=5 subcmd=0x01`.
> Оставлен для юникаст-совместимости со старым ПО.

## 6. Статус-пакет (stat_modem)

Модем раз в секунду шлёт `struct stat_modem` (66 байт) на адрес/порт, заданные
командой `0xA0 group=3` (только при `status_on=1`). Содержит: температуры (FPGA,
AD9361), счётчики TX/RX, и по RX — `min_pow/max_pow/acc_pow` (RSSI) и
`min_gain_index/max_gain_index` (АРУ). Подробно про RSSI/АРУ/MER/созвездие — см.
`docs/MEASUREMENTS.md`.

## 7. Типовые сценарии

**Найти и настроить модем с неизвестным IP:**
1. `get config` broadcast'ом → в ответах видно `device_id` + текущий IP каждого модема.
2. Выбрать нужный по `device_id`.
3. `set IP` / `set role` / `set MAC` broadcast'ом с `tid` = его `device_id` — применит
   только он.
4. Повторный `get config` — проверить.

**Cross-subnet (ПК и модем в разных подсетях, но на одной линии):**
- Запрос — limited broadcast `255.255.255.255` (модем принимает как свой broadcast).
- Ответ off-subnet модем шлёт **тоже broadcast'ом** (`resp_send` → `udp_sendto_if`
  через `bridge_netif`), т.к. юникастом маршрута назад нет.
- На хосте для приёма broadcast-ответа нужен сокет, привязанный к `0.0.0.0`
  (см. `scripts/broadcast_test.py`).

**Сменить роль подключённого модема (юникаст):**
- `A0 05 00 00 00 <role>` (tid=0) на IP модема → сменит роль и IP на дефолт роли.

## 8. Watchdog (кратко)

Аппаратный **SCU watchdog** Zynq защищает от зависаний:
- пинается в главном цикле после обработки сети; если цикл завис — WDT перезагружает CPU;
- при старте читается причина прошлого ребута (`REBOOT_STATUS`), логируется;
- рантайм-тумблер: `0x90 0x4C` (вкл/выкл), статистика: `0x90 0x40` (счётчики
  пинков/голоданий, uptime, секция-«виновник» последнего краха);
- дефолт вкл/выкл — `WDT_ENABLED_DEFAULT` в `platform_config.h`.

Подробно — см. `docs/WATCHDOG.md` и отчёты `docs/wdt_*`.

## 9. Ограничения (текущее состояние)

- **По умолчанию в RAM:** роль/IP/MAC/device_id сбрасываются при перезагрузке к
  дефолтам роли — **если не сохранить** их во флэш командой `0x20` (§4.4). После
  сохранения конфиг переживает ребут и пропадание питания.
- **`device_id` задаётся вручную** через `DEVICE_ID_DEFAULT` (per-device define).
  Настоящий аппаратный уникальный ID (из flash UID) — на будущее.
- **Радио-формат с `device_id` в сегменте** несовместим со старым: **обе платы
  (master и slave) прошивать одновременно**, иначе рассинхрон потока → CRC-фейлы.
- Разные аппаратные платформы (AntSDR / макет ПКРВ / ZedBoard) — по-прежнему разные
  битстримы; унифицирована только программная часть.

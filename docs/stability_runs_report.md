# Отчёт по прогонам стабильности модема (radio bridge)

Серия нагрузочных тестов прошивки `debug_wdt_merged` (SPI-чтения отключены
`#if 0`, IQ-стрим по умолчанию OFF). Цель — найти причину постоянных
WDT-ребутов и определить устойчивую рабочую точку по пропускной способности.

---

## Стенд

Один ноутбук, две USB-Ethernet карты, два модема, связанных по радио.

```
netns "slaveside"                                          main ns
NIC 8dd (192.168.250.10) ──GEM── slave ──радио── master ──GEM── NIC 7870 (192.168.250.22)
   "камера / источник"                                        "дисплей / приёмник"
```

- slave-карта вынесена в network namespace — иначе ядро Linux заворачивает
  трафик к `.10` через loopback и он не идёт через радио.
- Нагрузка: `iperf3 UDP` из netns (slave) → main ns (master). Физический путь:
  slave-NIC → slave модем → радио → master модем → master-NIC.
  Это **реальное направление видео** (камера на slave → дисплей на master).
- Скрипты: `scripts/load_slave_to_master.sh`, `scripts/stability_monitor.py`.

## Методика измерения

- **Монитор ребутов** (`stability_monitor.py`): каждые 5 сек шлёт `0x90 0x40`
  на оба модема, ловит падение `uptime_sec` (= ребут), пишет `crash_section`,
  `oldest_hb`, `starve_mask`, `reboot_status`.
- **Radio + lwIP stats** (`0x90 0x20`) после прогона: `seq_gap`/`pkt_gap`/`crc`
  (потери радио), `fifo_full`/`rx_ovf` (FIFO), `heapERR`/`poolERR` (lwIP-буферы).
- **MER** считывался оператором с виджета созвездия в Qt перед прогоном.

## Эволюция гипотез — что проверяли и что вышло

1. **SPI-залипы** (`AD9361_TEMP`/`SPI_RSSI` в crash_section) — РЕАЛЬНАЯ проблема,
   busy-wait без таймаута в `spi_engine.c:590` (`while(sync_id != _sync_id)`).
   Отключили SPI-чтения (`#if 0`) → эти ребуты ушли. **Отложено** (вернуть с
   таймаутом / hw-reset SPI engine).

2. **System WDT backstop** — добавляли (ветка `debug_swdt_spi`), дало
   нестабильность на старте (boot-loop, вероятно неверный CRV-таймаут).
   Откатили. **Отложено** (пересчитать таймаут от реального CPU_1x).

3. **IQ-стрим (8.5 Mbps, 1000 pbuf/сек)** — РЕАЛЬНАЯ нагрузка, забивает lwIP.
   По умолчанию OFF, включается `0x90 0x47`. Замер: 8.5 Mbps при дефолте —
   в 7× больше видео. **Нужен throttle** (раз в 50 мс) когда понадобится.

4. **Деградация радио / AGC после soft-reset** — гипотеза была: WDT-ребут не
   сбрасывает AD9361 аппаратно → AGC кривой → линк сыпется → каскад.
   **ОПРОВЕРГНУТО**: на прогонах MER23/MER27 с чистым линком (seq_gap=2)
   модемы всё равно ребутятся. Ранние «обвалы радио» (60k seq_gap) были
   *следствием* reboot-каскадов, а не причиной.

5. **Нехватка lwIP-буферов** — ОПРОВЕРГНУТО: `heapERR=0`, `poolERR=0` во всех
   прогонах, pool на пике 66-155 из 256. Буферов в избытке.

6. **Потолок пропускной (backpressure-спираль)** — **ПОДТВЕРЖДЕНО**. См. ниже.

## Главный вывод

**Устойчивый потолок бриджа slave→радио ≈ 1.0 Mbps** (при текущей модуляции/коде).

| Битрейт | Поведение |
|---|---|
| **≤ 1.0M** | стабильно (с чистого POR — 0 ребутов 15 мин; из грязного старта — 1 осадочный, потом держит) |
| **1.5M** | reboot-цикл через ~2 мин |
| **2.0M** | непрерывный reboot-каскад |

Математика 1M-эталона: 699681 блоков / 900с ≈ 777 блоков/сек × 188 байт × 8 ≈
**1.17 Mbps** — сходится с iperf 1M + overhead.

### Природа бага

Все `LWIP_INPUT`-ребуты — это **перегрузка**, а не радио/буферы/SPI:
- slave принимает поток по GEM от ноута, должен пробросить в радио;
- если поток > устойчивой ёмкости радио → GEM-RX backlog растёт →
  `xemacif_input` гребёт всё большую пачку за вызов → однажды проход >2 сек →
  WDT срабатывает (`mask` до `0xF` = main loop мёртв >5 сек).
- **Перегрузка вешает `xemacif_input` вместо честного дропа пакетов.**
  В поле любой источник выше ёмкости радио уронит модем в reboot-цикл.

WDT при этом отрабатывает корректно (ловит soft-hang, ребутит, модем
восстанавливается) — но линк рвётся постоянно.

## Заметки оператора (MER по прогонам)

- Стартовый MER гулял **6 → 15 → 23 → 27** между прогонами в зависимости от
  состояния (после каскадов ребутов хуже, после чистого POR + аттенюации лучше).
- soz.jpg: **MER 6.38** — созвездие 8-PSK деформировано, точки скучены в центре,
  AGC сорван (это было после серии ребутов, не с чистого старта).
- **MER не коррелирует с ребутами**: при MER 23-27 (чистый линк, seq_gap единицы)
  модемы всё равно падали на 1.5M/2M. Стабильность определяется битрейтом, не MER.
- Аттенюация (добавлена перед MER23-прогоном) улучшила качество линка
  (seq_gap c десятков тысяч до единиц), но на ребуты от перегрузки не повлияла.

## TODO / следующие шаги

1. **Фикс робастности (приоритет):** перегрузка должна **дропать**, не вешать
   `xemacif_input`. Варианты:
   - ограничить пакетов-за-проход в `xemacif_input` (не грести весь backlog);
   - ранний drop в bridge/`radio_linkoutput` когда radio TX-ring заполнен выше
     порога (сейчас дропает только при полном — поздно).
2. **Поднять потолок пропускной:** ускорить bridge→radio path (CRC32, tx_process),
   либо поднять модуляцию/символьную скорость радио (согласовать с PL).
3. **SPI с защитой:** вернуть `ad9361_get_temperature`/rssi с таймаутом в
   `spi_engine.c` busy-wait + hw-reset SPI engine при залипе.
4. **AD9361 hw-reset при битом RX:** дёргать RESETB при лавине seq_gap/crc
   (восстановление AGC) — требует рабочего SPI.
5. **IQ-стрим throttle:** раз в 50 мс вместо каждого блока (8.5M → ~160 kbps).
6. **System WDT backstop:** пересчитать CRV от реального CPU_1x, стартовать
   после первого прохода main loop (ветка `debug_swdt_spi`).
